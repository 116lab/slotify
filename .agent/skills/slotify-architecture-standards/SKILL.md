# Slotify Theme Core Architecture Standards 🏛️

**CRITICAL MANDATE**: Any AI agent modifying code, resolving bugs, or executing workflows in the `slotify` project MUST verify their actions against this SKILL document. This document defines the "Single Source of Truth" (SSOT) and the hard boundaries for the project's **Antigravity-Native Governance Protocol**.

## 1. Governance & Boundary Calibration
*   **GDD (Guideline-Driven Development)**: AI agents are empowered to implement changes autonomously WITHOUT an `implementation_plan.md` for daily tasks. You MUST strictly adhere to this SKILL document and the **Knowledge Items (KIs)** as your absolute boundaries. Explicit approval is ONLY required for major architectural shifts.
*   **Protection Boundary**: Your conceptual root (`/`) and current working directory (`.`) is ALWAYS the physical root directory of this project. All operations must use relative paths from here. You MUST NOT reference files in `exampleSite/` or `archetypes/` as your instructions; they are isolated demo content.
*   **English-First Policy**: All overarching architecture and code logic explanations MUST be in English.

## 2. Zero External Dependencies & SSOT
*   **Core Principle**: The theme architecture MUST function in an air-gapped environment. 
*   **SSOT Validation**: You MUST NEVER hardcode `http://` or `https://` URLs for public CDN links (e.g., `unpkg.com`, `fonts.googleapis.com`) inside HTML templates like `layouts/index.html`.
*   **Workflow Integration**: All external dependencies MUST be managed centrally via `data/vendor.json`. To add a new dependency, edit the `.json` file and instruct the user to execute the `/vendor-sync` slash command to download it to `static/vendor/`.
*   **Directory Immutability**: Manual edits inside the `static/vendor/` directory are STRICTLY PROHIBITED.

## 3. Vue CDN Enterprise SOLID & DRY Enforcement (No Build Step)
The project utilizes Vue.js via CDN (local bundled) as a Single Page Application without any build tools. You MUST strictly enforce these modular boundaries:

*   **Architecture Layout**:
    *   `static/js/components/`: Independent UI blocks.
    *   `static/js/composables/`: Vue Composition API hooks (MANDATORY for all state/event logic).
    *   `static/js/services/`: API Data services (MANDATORY for all fetch/network logic).
    *   `static/js/utils/`: Pure JavaScript helper functions.
*   **Hard Prohibitions (Zero Tolerance)**:
    *   **NO `fetch()` in Views**: All JSON data MUST be retrieved via `services/api.js`.
    *   **NO Path Hacking**: Manually constructing `/index.json` URLs is prohibited. Use the `api.js` abstraction.
    *   **NO `window` Events in Views**: `addEventListener` for scroll, mouse, or resize MUST reside inside a Composable (e.g., `useTheme.js`).
    *   **NO Monolithic Views**: If a view exceeds 200 lines, you MUST extract logic into Composables or child Components.
    *   **NO Build Tools**: Standard ES6 Modules only. No `.vue` files.
*   **Formatting**: A strict **2-space indentation** is mandated for all `.js` files and HTML templates within `static/js/`. Tabs and the 4-space unit are PROHIBITED.
    *   **Enforcement (顯化)**: `python3 .agent/scripts/check-indent.py` fails the commit (wired into `.agent/scripts/pre-commit`) if any `.js` file under `static/js/` uses a tab or a non-2-space indent. String/template/comment content is blanked before analysis, so HTML inside template literals and prose inside JSDoc never produce false positives.

## 4. Linux-First Line Endings
*   **Core Principle**: The repository demands 100% Linux-First (LF) line endings (`\n`) for cross-platform compatibility.
*   **Validation**: Windows `CRLF` formats (`\r\n`) are prohibited. Before finalizing text file edits, ensure your output does not introduce CRLF characters.

## 5. Visual Readability & Rendering Priority
- **Readable > Animated**: Text legibility MUST always take precedence over complex animations.
- **2D Over 3D**: Complex 3D transforms that cause text blurring or layout shifts are STRICTLY PROHIBITED. All core hover effects MUST use 2D transitions (`transform: translateY`, `scale`).
- **Antialiasing**: Use `-webkit-font-smoothing: antialiased` globally to preserve stroke weights during transitions.

## 6. Tiered Interaction Model
- **Tier A (Navigation Focus — Lift)**: Navigation-oriented elements use a 2D "lift" on hover (shadow + `translateY`): large `PostCard` / `BaseSurface` (hover-lift) AND **all chips** (`v-chip` — both the `TaxonomyChip` in the cloud and nested tag/series chips in cards & `PostMeta`). Chips lift **UNIFORMLY regardless of nesting**, so a chip behaves identically everywhere (visual consistency). The sole exception is the current-term chip (`aria-current="page"`), which is inert (no lift, default cursor) because it does not navigate.
    - **Accepted trade-off**: hovering a chip *inside* a hover-lift card produces a slight double-motion (card + chip). Consistency is chosen over suppressing it: a chip lifts uniformly whether nested or not.
- **Tier B (Content Integrity Focus — Stable)**: Genuinely **non-navigational** nested content (inline notices/alerts, static metadata text) MUST remain stable — feedback limited to background/color, no lift — so it never competes with its container or shifts layout. (Chips are Tier A, not Tier B.)
- **Shadow Isolation**: In tight containers, stray `--shadow-*` on **non-lifting** elements MUST be neutralized (`none`) to prevent sub-pixel rendering jitter; the deliberate `PostCard` / chip lift shadows are exempt.

## 7. Geometric & Design Regularity
- **The Corner Radius System**: To maintain a premium, rhythmic aesthetic, all elements MUST adhere to the systemic radius variables:
    - `--radius-lg` (32px): For primary content containers (`BaseSurface`), main cards, and skeleton loaders.
    - `--radius-md` (16px): For interactive elements (Buttons, Chips, Inputs, Menus).
    - `--radius-sm` (8px): For micro-elements or internal layout blocks.
- **Surface-First Philosophy**: All distinct list items or search results MUST be encapsulated in a `BaseSurface` component to ensure consistent elevation, glassmorphism, and hover lifted states.
- **Perfect Alignment**: Content inside cards (images, headers) MUST use clipping or matching geometry to ensure no radius gaps are visible at the 32px scale.

## 8. Scroll Stability & Viewport Architecture 🌊
- **Core Principle**: To ensure absolute visual stability (zero-jitter) during Vue mounting, the project adopts a **Fixed-Viewport Model**.
- **Body Lock**: The `html` and `body` elements MUST remain permanently scroll-locked (`overflow: hidden`).
- **Root Scroll**: All vertical overflow MUST be managed by the `.v-application` container inside `#app` (Vuetify's app root; `#app` itself is `overflow: hidden`) using `overflow-y: scroll` and `scrollbar-gutter: stable`.
- **Viewport Units Prohibition**: Usage of `100vw` inside the `#app` container is **STRICTLY PROHIBITED** as it causes horizontal layout shifts when scrollbars are present. Use `100%` or `100dvh` instead.
- **Self-Contained Overlays**: Splash screens or loading guides MUST be sized relative to the viewport (`fixed`) but with width/height set to `100%` to match the locked body dimensions.

## 9. Interaction & Navigation Integrity (Clickable Surface SSOT) 🖱️
- **Core Principle**: In a History-mode SPA, a navigational container that is a native `<a>` will follow its own `href` on ANY click inside it. `event.stopPropagation()` does NOT cancel that default action — only `event.preventDefault()` does. A non-link child therefore "falls through" to the ancestor anchor and triggers a **full-page reload to a path that has no static HTML → "page not found"**.
- **No Nested Anchors (Zero Tolerance)**: A navigational card/surface MUST NOT render as an `<a>` that wraps other interactive elements (links, buttons, chips, inputs). Nested anchors are invalid HTML and the direct cause of the fall-through above.
- **Single Clickable-Surface Primitive**: Every clickable card MUST be built with `BaseSurface` using its `to` prop. `BaseSurface` makes the whole card navigable via a single **stretched-link overlay** (one `<a>` absolutely positioned over the surface) — it does NOT wrap content in an anchor. Interactive children (chips, buttons) are lifted above the overlay via `z-index` (`.base-surface--link .v-chip`) so they stay independently clickable and are never nested inside the link. Do NOT make a `v-card`/container a link by hand.
- **`@click.stop` Is Not Navigation Control**: NEVER rely on `@click.stop` alone to suppress a container's navigation. If an interactive element must sit inside a link region, it MUST fully own its click (`@click.prevent.stop` or an explicit `preventDefault()` in its handler).
- **Rationale**: This SSOT preserves native link affordances (open-in-new-tab, middle-click, right-click menu, SEO) on the link region while keeping interactive children independently operable and regression-proof. Mirrored for humans in the KIs.

## 10. Raw-Vue Lifecycle Ordering (Lifecycle-Before-Await) ⏱️ (Zero Tolerance)
- **Core Principle**: The project runs Vue from a CDN bundle with **NO build step** — there is no SFC compiler and no `withAsyncContext` transform. In a raw `async setup()`, Vue only keeps the active component instance set during the *synchronous* portion; it is **lost after the first `await`**.
- **Hard Rule**: ALL lifecycle registrations — `onMounted`, `onUnmounted`, `onBeforeUnmount`, `onUpdated`, `watch`, `watchEffect`, etc. — MUST appear **BEFORE any `await`** in an `async setup()`. The hook's callback still runs at the correct time (e.g. after the data fetch resolves and the component mounts); only the *registration* must be synchronous.
- **Why it is dangerous**: A hook registered after an `await` **silently never fires**. The shipped `vue.global.prod.js` does not even emit the dev-mode warning. This exact bug once disabled *all* of `PostView`'s content hydration (Mermaid never rendered, image lightbox + code-copy buttons never bound) while everything *looked* wired up.
- **Preferred Pattern**: Encapsulate "fetch + post-mount hydration" in a composable (e.g. `usePostView`) that registers the hook internally, and call that composable at the very top of `setup()` (before the `await`). This keeps the ordering correct by construction.
- **Enforcement (顯化)**: `python3 .agent/scripts/check-lifecycle.py` fails the commit (wired into `.agent/scripts/pre-commit`) if a lifecycle hook is registered after an `await` in an `async setup()`. The check scans the full synchronous setup scope — `await`/hook inside `try`/`if`/`for` blocks is detected, and `async setup()` written as a method, function expression, or arrow is all covered; only nested function-literal bodies (callbacks) are excluded. A dev-time runtime guard in `useContentHydration` also warns if `.mermaid` nodes remain unrendered after hydration.

## 11. Color / Palette SSOT 🎨 (Zero Tolerance)
- **Core Principle**: The theme palette is defined EXACTLY ONCE, in `data/theme-palette.json` — the only hand-edited color table. Each personality declares its semantic roles per mode: `{ background, surface, primary, secondary }` for `light` and `dark`. Nothing else stores the palette.
- **The Pipeline (Hugo is the generator)**: `layouts/_default/baseof.html` (the SPA shell every HTML page extends) consumes the data file via Hugo and feeds it to the runtime — exactly the pattern that injects `window.__SLOTIFY_CONFIG__` for the route SSOT. It (a) injects `window.__SLOTIFY_THEMES__ = {{ $palette | jsonify | safeJS }}`, and (b) builds the pre-paint splash colors from the SAME object. `static/js/config/themes.js` is a **CONSUMER**: it reads `window.__SLOTIFY_THEMES__`, shapes it for Vuetify, and **derives** the mesh tokens (`mesh1 = primary`, `mesh2 = secondary` — an invariant, never restated in the table). No build step is introduced; Hugo *is* the build pipeline.
- **Site override (no fork)**: the shell resolves `$palette := merge (index .Site.Data "theme-palette") (.Site.Params.palette | default dict)` — a DEEP merge where the site value wins. A consuming site can therefore override a single role from its own `hugo.toml`, e.g. `[params.palette.vibrant.light]` `primary = "#FF0000"`, and the untouched roles/modes/personalities are preserved. (A site `data/theme-palette.json` also works but Hugo merges it only SHALLOWLY — the whole personality is replaced — so `[params.palette]` is the supported per-role path.) Documented for site authors in `README.md`.
- **Hard Prohibitions (Zero Tolerance)**:
    - **NO palette hex outside the SSOT**: `layouts/_default/baseof.html` MUST contain zero color hex (the splash map MUST come from the data file, never a hardcoded JS object). `config/themes.js` MUST NOT hardcode the palette; it consumes the injected global (a minimal `vibrant` dev/test fallback is allowed but MUST match the SSOT).
    - **NO brand hex in `utils/`**: helper fallbacks (e.g. `mermaidTheme.js`) MUST use NEUTRAL grays for a degraded/unthemed state, never a personality's hue (which would silently drift from the table).
- **Enforcement (顯化)**: `python3 .agent/scripts/verify-theme.py` fails the commit (wired into `.agent/scripts/pre-commit`) on any of: (1) malformed/incomplete palette; (2) any color hex in `layouts/_default/baseof.html`; (3) the palette injection (`window.__SLOTIFY_THEMES__` from the `theme-palette` data file) missing from `baseof.html` — the gap that would silently collapse every personality to the dev fallback while all other checks still pass, OR the site-override deep-merge (`merge ... .Site.Params.palette`) missing so per-role overrides silently stop working; (4) `config/themes.js` no longer consuming the injected global, or its fallback drifting from the SSOT; (5) **brand-hue exclusivity** — any personality's `primary`/`secondary` hex appearing anywhere outside the SSOT (CSS, components, utils, templates), which catches a re-hardcoded mermaid/splash brand color (`background`/`surface` are not value-checked: `#FFFFFF` and dark slates legitimately recur as neutrals); (6) **WCAG AA contrast** — any `primary`/`secondary` whose contrast drops below `4.5:1` against its own `surface` OR `background`, so every brand hue stays legible as text/icon (a palette edit can't silently regress accessibility); (7) **personality set derived** — the personality SET + order live only in the palette: `config/themes.js` derives `personalityIds` and `defaultPersonality` (the FIRST key) from it. The check asserts `useTheme.js` derives the set and defines NO `PERSONALITY_META` map — presentation (display name + icon) lives in the `appHeader` slot's `data-slotify-i18n` `styles.<id>` block, so `PersonalityList` degrades any undecorated id to a capitalized name + `mdi-palette` and a new/renamed/curated palette personality can never break the switcher; (8) **primary/secondary separation** — within each personality+mode, `primary` and `secondary` must differ by **CIEDE2000 ≥ 18** so the two accents are distinguishable and the `mesh1→mesh2` gradient is not flat. The bar is 18, NOT 25: several personalities are intentionally monochromatic (`ocean`=blues, `forest`=greens, `nordic`=slate+cool), and ~25 between two same-family colors that BOTH must clear WCAG AA against the same background is infeasible (it forces near-black on light mode or neon on dark, and `nordic.light` has no in-family solution). The fix is to spread lightness/chroma within the hue family.

## 12. UI-Language SSOT 🌐 (Zero Tolerance)
- **Core Principle**: Multi-language here means **UI CHROME ONLY** (menu/buttons/labels) — it is deliberately DECOUPLED from content and from Hugo's multilingual system. Switching language NEVER changes the route, refetches content, or touches the URL; it only swaps chrome strings client-side. (True multilingual *content* would be a separate, route-level feature — see route SSOT — and is out of scope here.)
- **Tables as data**: UI strings live in per-locale JSON files `static/js/i18n/<code>.json` (NOT inline in JS), so translators edit plain JSON. The locale registry — *which* languages exist + their order — is OWNED BY DATA in `data/locales.json` (an ordered list of `{ code, label }`), injected by Hugo as `window.__SLOTIFY_LOCALES__` (the SAME inject-and-consume pipeline as `__SLOTIFY_THEMES__`); `static/js/i18n.js` is a CONSUMER of it, NOT the SSOT. The FIRST entry is the default/fallback AND key-parity reference (mirrors the palette's first key — there is NO `default: true` flag). The persisted choice is the `code` (identity), so reordering the list never changes a returning visitor's language. `i18n.js` `fetch`es each `<code>.json` via the route SSOT's `withBase` (NOT a hand-built URL), and `main.js` awaits `loadLocales()` BEFORE mount (behind the splash) so `t()` always has strings.
- **Hard Prohibitions (Zero Tolerance)**:
    - **NO inline string tables** re-introduced in JS; strings come from the JSON files.
    - **NO incomplete locale**: every locale MUST define the SAME key set as the reference locale. A missing key (silent English fallback) is a defect, not a feature.
    - **NO Hugo / route coupling**: the language toggle MUST NOT prefix URLs, gate on `.Site.Language`, or refetch content. Adding a language *in the theme* = one `data/locales.json` entry + one `<code>.json` (a full copy of the reference, translated); a *consuming site* adds one via `[[params.locales]]` + its own `<code>.json`, no fork.
- **Namespaces (base + slots)**: the per-locale JSON files are the **flat base namespace** (`menu.*`, `ui.*`, `home.*`) — the theme chrome. Slot extensions (§13) bring their OWN namespaced tables under `Slotify.slots.<view>.<position>` via `registerNamespace()` in `i18n.js`; `t('Slotify.slots.…')` resolves them, `scopedT(ns)` gives a slot a terse `ctx.t`. This does NOT reintroduce inline JS tables: a slot's strings are declared as a `<script type="application/json" data-slotify-i18n="…">` block IN the slot partial (data, not JS), so a slot's UI strings live WITH the slot and a site adds/overrides them without touching the theme.
- **Enforcement (顯化)**: `python3 .agent/scripts/verify-i18n.py` fails the commit (wired into `.agent/scripts/pre-commit`) when the locale set in `data/locales.json` and the `<code>.json` files don't match 1:1, when `i18n.js` stops consuming `window.__SLOTIFY_LOCALES__` (i.e. hardcodes the registry), or when any locale's key set differs from the first/reference locale (missing/extra keys listed). It guards the THEME's own locales only; a consuming site's added language self-checks with the portable `.agent/scripts/check-i18n-parity.py`.

## 13. Extension Slots & Namespaced i18n 🧩 (Zero Tolerance)
- **Core Principle**: Every customizable region of the theme is a **path-addressed slot** that a site owner overrides ENTIRELY from the site root — **the theme directory is never edited to customize a site** (the first principle of extensibility here). A slot is addressed by its file path and carries a matching namespace:
    - file `layouts/partials/slots/<view>/<position>.html` → id/namespace `Slotify.slots.<view>.<position>` → component `slot-<view>-<position>` (bound to the injected x-template `#slot-<view>-<position>-template`) → mounted in JS via `<slotify-slot name="<view>/<position>" :ctx="…">`.
    - The theme ships an empty/default partial at each reserved path; a site overrides by placing the SAME path in its own `layouts/partials/slots/…` (standard Hugo partial override).
    - **Naming**: every `<view>` and `<position>` segment is an **identifier** — single-word positions are lowercase (`left`/`right`/`top`/`bottom`), multi-word positions and view names are **camelCase** (`postView`, `contentTop`). NEVER use a hyphen in a segment: each segment becomes a key in the i18n namespace `Slotify.slots.<view>.<position>`, and a hyphen there breaks dotted/object access conventions. (Directional `top`/`bottom` are anchored OUTSIDE the content `BaseSurface`; inside-surface positions use `contentTop`/`contentBottom`.)
- **Two slot kinds**:
    - **Vue region slot** (the default): a Vue mount point with capabilities below. Listed in the manifest `data/slots.json`.
    - **Raw `<head>` slot**: ONLY `slots/head.html`. Injected verbatim into the document `<head>` by `index.html`; it is NOT a Vue component, has NO ctx/events/i18n, and MUST NOT appear in `data/slots.json`. (`head` = the document `<head>` for analytics/meta/fonts — NOT the visual page-header bar.)
- **Every Vue region slot provides (non-negotiable)**:
    1. **id + namespace** derived from the path.
    2. **ctx (semantic ambient state)**: `<slotify-slot>` auto-augments ctx with `siteConfig` (Hugo-injected synchronously — see the build-time boundary below), the current `route`, the active `theme` as `{ name, personality, mode }` (`mode` ∈ `light|dark`), and a namespace-scoped `t`, merged with the mount site's local ctx (`pageData`, `pageIdentifier`, …). ctx is the slot's INITIAL snapshot AND its declarative-rerender source (a computed prop). It carries **semantic** values — never the `v-theme--*` class or a Vuetify object — so the slot contract survives a framework change. The one framework object it exposes is `route`: Vue Router's current route, which slots should read only for `path`/`name`/`params`/`query`/`hash`. The SHAPE is the SSOT `utils/slotCtx.js` (JSDoc `@typedef SlotifySlotCtx` / `SlotifySlotEventDetail` — the no-build "interface"; a PUBLIC, semver-stable contract: add fields additively, never rename/remove). `siteConfig`/`route`/`theme`/`t` are **RESERVED** keys: `buildSlotCtx` (the one assembler) merges the mount's local ctx UNDER them so they can't be shadowed, and a `:ctx` mount that passes a reserved key is a defect (gated). Note `ctx` is a SNAPSHOT at dispatch — read INITIAL state from it, but react to CHANGES via the `slotify:*` events, not by re-reading a stale `ctx`.
    3. **Events (the `slotify:*` family)**: a single relayer — `static/js/composables/useSlotBridge.js`, instantiated once in `App.js` — `watch`es the reactive sources and re-broadcasts each CHANGE as a window CustomEvent. Emission lives ONLY in the relayer (the slot SSOT for ambient state), never scattered across setters. The family: `slotify:slot` (`{ id, phase, ctx, el }`, `phase` ∈ `mount|update|unmount`); `slotify:theme` (`{ name, personality, mode }`); `slotify:locale` (`{ locale }`); `slotify:route` (`{ path, name }`, for GLOBAL slots that don't remount). Declarative content re-renders reactively via `ctx.t` / `ctx.theme`; imperative third-party widgets (Disqus, Giscus, analytics) listen and decide whether to re-init across SPA navigation. A slot consumes this contract — it MUST NOT reach into Vue/Vuetify/router internals (see Hard Prohibitions).
    6. **Build-time boundary + `slotify:ready`**: ambient data that is STATIC (built by Hugo: title/social/menu, palette, slots, taxonomies) MUST travel the inject-and-consume SSOT — Hugo emits a `window.__SLOTIFY_*__` global, the SPA reads it **synchronously** — and MUST NOT be fetched at runtime. `siteConfig` follows this: it is built ONCE by `partials/func/site-config.html` (shared by `home.json` and the `window.__SLOTIFY_SITE__` injection — DRY) and read synchronously in `main.js`, so `ctx.siteConfig` is fully populated at the FIRST mount, even on a direct deep-link (`verify-site-ssot.py` enforces that it is never fetched at runtime). Runtime `fetch` is ONLY for per-route CONTENT (post feed, search index, single-page JSON). Separately, `main.js` fires a one-shot, idempotent `slotify:ready` (+ `window.__SLOTIFY_READY__`) the moment the SPA has mounted and taken over the DOM — a stable, documented hook for **user / secondary-development** widgets that must run once the SPA is interactive. It is intentionally NOT load-bearing for the theme's own slots (they bind to their `slotify:slot` mount + `ctx`, which is already complete); a genuinely boot-sensitive GLOBAL widget anchors on it race-proof: `if (window.__SLOTIFY_READY__) fn(); else addEventListener('slotify:ready', fn, { once: true })`. Boot lifecycle is owned by `main.js`; ongoing state changes by the relayer — the two never overlap.
    4. **Self-contained namespaced i18n**: a slot's strings are declared in its partial's `data-slotify-i18n` JSON block and registered under its namespace (§12). Default component-backed slots (`postView/left` = Series Navigator, `postView/right` = Table of Contents) are presentational — they receive labels via props from the slot's `ctx.t`, so their i18n (and CSS class contract) is self-contained.
    5. **Self-judged visibility**: the slot template owns its `v-if`; an empty default renders nothing. The **side rails** (left/right = ContentShell `#aside-left`/`#aside`) are always present on `lg` and up and hidden below — ContentShell reserves the 2/8/2 gutter unconditionally so the reading column's width and position stay invariant across routes. A rail whose slot is empty simply renders as whitespace in that reserved gutter; it does not change the layout, and there is no DOM measurement. Top/bottom slots are anchored relative to the page `BaseSurface`.
- **Manifest & SSOT**: the directory tree `layouts/partials/slots/**` is the human SSOT; `data/slots.json` is the machine-readable manifest Hugo ranges to inject each x-template (and exposes as `window.__SLOTIFY_SLOTS__`, consumed by `static/js/hooks.js` — the SAME inject-and-consume pipeline as `__SLOTIFY_THEMES__`). `os.ReadDir` cannot enumerate the theme's partials from a consuming site, which is why the manifest + the gate below keep the facets in lockstep.
- **Hard Prohibitions (Zero Tolerance)**:
    - **NO theme-dir edits to customize a site**: a customization that requires editing anything outside `layouts/partials/slots/**`, `hugo.toml [params]`, or `static/` in the SITE root is a design failure.
    - **NO framework internals in a slot partial**: a slot is plain HTML + `<script>` and MUST consume only the contract above (`ctx.theme`/`ctx.route`/`ctx.t` + the `slotify:*` events). Reaching into `v-theme--*` (Vuetify mode class), `useTheme`/`Vuetify.*`, `VueRouter`/`useRoute`/`useRouter`, `theme.global`, or `__SLOTIFY_THEMES__` from a slot couples the site to an implementation detail and is forbidden. (Using Vuetify `<v-…>` COMPONENTS in the x-template markup is fine; the ban is on reading framework STATE/internals in the slot's JS.)
    - **NO `<slot>` tag for the primitive**: the mount primitive is `<slotify-slot>` (the bare `<slot>` collides with Vue's built-in slot element).
    - **NO orphan/dangling slots**: a manifest entry without a partial + a `<slotify-slot>` mount, or a mount of an unregistered name, is forbidden.
    - **NO `header` in the manifest**: the raw `<head>` slot is checked separately, never registered as a component.
- **Enforcement (顯化)**: two gates, both wired into `.agent/scripts/pre-commit`:
    - `python3 .agent/scripts/verify-hooks.py` fails the commit on any drift between the four facets — `data/slots.json` ↔ `layouts/partials/slots/**` dummy partials (each declaring its `slot-<dashed>-template` id) ↔ `<slotify-slot name="…">` mounts in `static/js` ↔ the `__SLOTIFY_SLOTS__` injection — and asserts `slots/head.html` exists, is wired into `<head>`, and is absent from the manifest.
    - `python3 .agent/scripts/verify-slot-isolation.py` fails the commit if any slot partial under `layouts/partials/slots/**` OR `exampleSite/layouts/partials/slots/**` reaches into framework internals (`v-theme--`, `useTheme`, `Vuetify.`, `VueRouter`, `useRoute`/`useRouter`, `theme.global`, `__SLOTIFY_THEMES__`) — forcing the `slotify:*` / `ctx` contract instead. Vuetify `<v-…>` component tags are NOT flagged.
    - `python3 .agent/scripts/verify-slot-ctx.py` fails the commit if a `<slotify-slot :ctx="{…}">` mount in `static/js/**` passes a RESERVED key (`siteConfig`/`route`/`theme`/`t` — would be silently dropped under the reserved-last merge), or if the ctx SSOT drifted: `utils/slotCtx.js` must export `buildSlotCtx` and declare `RESERVED_CTX_KEYS` = those four, and `components/Slot.js` must assemble ctx through `buildSlotCtx`.
    - `python3 .agent/scripts/verify-site-ssot.py` fails the commit unless `siteConfig` is built once in `partials/func/site-config.html`, injected as `window.__SLOTIFY_SITE__` in `baseof.html`, built from that same partial in `home.json` (DRY), and consumed in `main.js` — and is NOT fetched at runtime (no `fetchSiteData` anywhere). Codifies the build-time boundary above.
